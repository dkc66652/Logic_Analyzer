### 10.4 移动和缩放波形的想法

##### 移动波形：

单指按下识别到坐标，移动8个像素px后，判定出现移动事件，后面按照px的移动，触发显示区s_cnt和e_cnt变化，第一次判定移动后，可以先读一次cnt范围，并将范围内的波形读出来，绘制到sdram里，下一个触摸中断只更改s_cnt和e_cnt，不修改绘制sdram，等待下一个帧中断，ltdc指向准备好的绘制sdram，这样做是为了减少cpu的占用，因为我不管修改多少次sdram，只会在ltdc中断触发时修改显示地址，修改完地址后，再立刻读一次cnt范围，修改绘制sdram，所以帧率是不变的，频繁的修改sdram，只会多占cpu，不会让帧率提高

##### 缩放波形：

两指按下，记录两指中心坐标和两指间的坐标间距，间距变化超过8px判定为缩放事件发生，以两指间的中心坐标为轴，按照比例放大两边的cnt间距，也是等待帧中断触发修改完ltdc扫描的sdram地址，再去修改一次绘制sdram，同时时间表尺也按比例变化

### 10.4  LVGL与FreeRTOS协同

在宏里面定义LV_USE_OS，可以创建创建互斥锁，lv_lock(); lv_unlock();，lvgl不允许在其它任务中修改对象，会造成内存访问冲突，lv_lock(); lv_unlock();用这个去夹住就可以用了，比如按键触摸需要立刻刷新一块区域，不过一般情况下，`lv_timer_handler()`里就能读坐标，然后根据坐标去判断控件区域是否按下，从而触发回调，在回调里去绘制就没问题，回调本身属于`lv_timer_handler()`

#define LV_USE_OS LV_OS_FREERTOS

以后，LVGL 使用三类 FreeRTOS 对象：

- **线程**：通过 `xTaskCreate()` 创建 `swdraw`，负责软件像素绘制。
- **互斥锁**：`lv_lock()/lv_unlock()` 对应递归互斥锁，防止多个任务同时操作 LVGL。
- **同步对象**：GUI 任务通知 `swdraw` 开始绘制，`swdraw` 完成后再通知 GUI 任务继续执行 flush。

我工程里的lvgl从整体上分为两部分，显示和触控，我创建的lvgl任务首先对显示和触控进行初始化，在while循环里，（1）调用lv_timer_handler()去执行控件回调，修改显示ram，触发flush回调，（2）添加显示任务的修改函数，用信号量将显示与触控、采集关联
另外创建触控任务，做几个事件判断，是否在触控区域出发了移动或缩放，这里也会修改信号量，事件组，去关联显示，控件的按下由lvgl触发状态更新

 GUI任务里不该做大量耗时操作，容易阻塞，比如大量的写sdram

### 10.5 使用DWT统计任务CPU占用

**<u>每一次统计都会测试波形显示占用的CPU和黑屏显示占用的CPU，这样基本能看出算法占了多少，方便优化，黑屏显示只要一种像素的RGB值，不需要消耗算法时间</u>**

#### 目前的显示方案：

为了尽可能提高帧率，在每一帧显示完成，触发帧中断后：
如果绘制区的数据已经准备好了，就需要将绘制区和显示区的sdram交换，ltdc去扫描准备好的绘制sdram，同时获取nowtick，得到i本次的波形绘制区域，通知绘制任务又可以开始绘制了
绘制区的波形范围，只能由帧中断获得并通知绘制任务，不能在别处获得，否则会因为多次绘制，错过一帧甚至多帧，反而降低了实际刷新率
当前 LTDC 时序下实测显示刷新率约为 `64.8 fps`，帧周期约为 `15.4 ms`，所以绘制 SDRAM 完成后通常只需等待下一个垂直同步点。

但是写sdram目前是通过CPU的，也就是这样的过程
帧中断触发，获取 nowtick，通知绘制任务（几 us）--->绘制任务按界面开启顺序逐路查询左窗口到 nowtick 的边沿--->每路复用同一个 500 字节列状态数组--->转换成该通道 `512 x 26` RGB565 横向条带--->DMA2D 按通道顺序搬运到 SDRAM 后缓冲--->最后一个开启通道完成后等待垂直消隐换帧。硬件始终采集六路，未开启通道不查询、不生成条带。

所以最终 CPU 空闲时间主要来自等待帧中断。波形绘制独立以后，大量 CPU 占用归入 `wave` 任务，不再阻塞 `lvgl` 任务。

波形换帧已经与 LTDC 垂直同步硬件绑定，让绘制速率能够非常稳定，这对于一个工程来说也是很好的

##### 独立波形任务后的实测结果

采用“LTDC 帧中断锁存 tick → 释放二值信号量 → `wave` 任务绘制后缓冲 → 垂直同步交换缓冲”的方案后，连续多个 5 s 统计窗口的数据几乎稳定不变：

```text
waveform refresh fps=25.00, frames=125
cpu usage, last 5 s:
  frame_test        0.00%
  cpu_mon           0.01%
  wave             68.67%
  IDLE             16.56%
  lvgl              9.17%
  touch             0.17%
  swdraw            5.37%
```

- `25 fps` 是该版本中 LTDC Layer 1 实际完成缓冲交换的帧率，也是逐像素写 SDRAM 方案在当时 CPU 绘制速度和任务优先级下的稳定吞吐率，并不是 LTDC 硬件固定帧率。
- `wave` 负责取数、解析并直接写波形 SDRAM；`lvgl` 不再承担波形像素绘制。
- `swdraw` 负责时间尺、文字、圆弧和控件等 LVGL 软件绘制。
- CPU 总忙碌率约为 `83.44%`，空闲率约为 `16.56%`；二值信号量不会累计过期帧，也不会补画已经错过的波形帧。

##### CPU直接填充黑屏的实测结果

保持与正常波形相同的帧中断驱动方式，每收到一次绘制信号量，就由 `wave` 任务将整个 `500 x 444` RGB565 波形后缓冲区填充为黑色。不读取和解析波形数据，也不绘制波形线，只测试 CPU 通过 FMC 写入 SDRAM 的开销：

```text
waveform refresh fps=25.20, frames=126
cpu usage, last 5 s:
  frame_test        0.00%
  cpu_mon           0.01%
  IDLE             44.10%
  touch             0.17%
  lvgl              0.41%
  swdraw            0.00%
  wave             55.28%
  log               0.00%
  total busy        55.90%
```

- 每帧填充 `222000` 个像素，共写入约 `444 KB` SDRAM；当时的旧测试代码由 CPU 循环执行 16 位写入，即一次写一个 RGB565 像素。
- 按 5 s 内完成 126 帧计算，`wave` 任务每帧约占用 `5 s x 55.28% / 126 = 21.94 ms` CPU 时间。
- 仅填充黑屏时 `wave` 已占用 `55.28%` CPU，说明当前波形显示的主要开销是 CPU 写完整块 SDRAM，而不只是波形取数和解析算法。
- 该测试仍由 LTDC 帧中断和双缓冲交换驱动，但临时基准程序主动限制在约 `25 fps`，因此可以与当时约 `25 fps` 的正常波形绘制结果直接比较。

##### 32行条带加memcpy：有波形时的实测结果

为了减少 CPU 对 SDRAM 的逐像素随机写入，改为每帧只读取和解析一次波形数据，然后使用一个 `500 x 32` RGB565 片内 AXI SRAM 条带缓冲区。每个条带先在片内 RAM 清零，只绘制与该条带相交的波形，完成后通过 `memcpy` 连续写入 SDRAM；`444` 行共分为 `14` 个条带。

```text
waveform refresh fps=45.40, frames=227
lvgl rendered=48.40 fps, avg=4087 us, flush=275, dirty=16745 px/frame
cpu usage, last 5 s:
  frame_test        0.00%
  cpu_mon           0.03%
  IDLE             25.53%
  touch             0.17%
  lvgl             13.16%
  swdraw            7.36%
  wave             53.72%
  log               0.00%
  total busy        74.47%
```

- 新方案的 `wave` 单帧 CPU 时间约为 `5 s x 53.72% / 227 = 11.83 ms`；旧方案约为 `27.47 ms`，单帧 CPU 时间下降约 `56.9%`。
- 波形帧率从约 `25 fps` 提高到 `45.40 fps`，同时总忙碌率从约 `83.44%` 降到 `74.47%`，说明分块连续复制有效。
- 新方案虽然每秒绘制了更多帧，但 `wave` 占用仍从 `68.67%` 降到 `53.72%`。如果把新方案仍限制在 `25 fps`，按单帧耗时估算，`wave` 约占 `29.6%` CPU。
- `25 fps` 不是 LTDC 固定值。波形提交只是在 LTDC 垂直消隐期完成，当前时序下的实测上限约为 `64.8 fps`；旧方案因为单帧绘制太慢，二值信号量合并了来不及处理的帧通知。
- 波形刷新更快以后，时间尺也更频繁地失效和重绘，因此 `lvgl` 和 `swdraw` 占用有所增加，`lvgl rendered` 上升到 `48.40 fps`。
- 有波形时尚未达到当前约 `64.8 fps` 的 LTDC 刷新上限，主要是因为 `wave` 任务还会被更高优先级的 GUI、触摸任务抢占，并且 CPU、LVGL、LTDC 仍在竞争 AXI/FMC/SDRAM 带宽。

##### 32行条带加memcpy：无波形黑屏实测结果

未开始采集且没有保留波形时，仍由每次 LTDC 帧通知唤醒 `wave` 任务。任务使用和正常波形完全相同的 `500 x 32` RGB565 条带缓冲，只执行片内 RAM 清零和连续 `memcpy`，不读取、解析或绘制波形：

```text
waveform refresh fps=64.80, frames=324
cpu usage, last 5 s:
  frame_test        0.00%
  cpu_mon           0.01%
  wave             45.58%
  IDLE             53.81%
  lvgl              0.41%
  touch             0.16%
  swdraw            0.00%
  log               0.00%
  total busy        46.19%
lvgl rendered=0.00 fps, avg=0 us, flush=0, dirty=0 px/frame
sdram cpu fill avg=7067 us, rate=62.82 MB/s, frames=323
```

- 黑屏填充达到 `64.80 fps`，说明新条带复制路径已经能够跟上当前 LTDC 的每一次帧刷新。
- DWT 实测每帧清零和搬运平均耗时为 `7.067 ms`；按任务占用反算为 `5 s x 45.58% / 324 = 7.03 ms/帧`，两种统计结果基本一致。
- 每帧向 SDRAM 写入约 `444 KB`，有效写入速度为 `62.82 MB/s`。旧逐像素黑屏方案约为 `21.94 ms/帧`，新方案单帧耗时降低约 `67.8%`，吞吐量约提高到原来的 `3.1` 倍。
- 正常有波形时 `wave` 约为 `11.83 ms/帧`，减去纯黑屏填充的 `7.067 ms/帧`，取数、解析和条带内波形绘制合计约增加 `4.76 ms/帧`。
- 黑屏期间没有时间尺失效请求，所以 `lvgl` 只占 `0.41%`，`swdraw` 为 `0%`；此时总忙碌率为 `46.19%`，空闲率为 `53.81%`。
- `waveform` 的 324 帧与 SDRAM 统计的 323 帧相差一帧，是两个统计快照边界不同造成的正常现象。

当前先使用 CPU `memcpy` 验证了片内 RAM 分块绘制的收益。后续可以将条带复制替换为 DMA2D，并使用两个条带做乒乓缓冲：DMA2D 搬运前一个条带时，CPU 同时计算下一个条带，从而进一步释放 CPU，并尽量保持或提高波形帧率。

**<u>代码运行的指令耗时，外加fmc需要等待主频进行时钟同步，单字节写的耗时会远远大于批量写入，这是需要在代码层面不断优化的</u>**

#### DMA2D优化方案：

使用乒乓缓冲，搬运RAM_DMA_BUFA的时候，绘制任务写RAM_DMA_BUFB，dma缓冲区的大小=波形条带的倍数*sdram宽度，保证波形不会被分成两段写入sdram，造成不必要的像素转换算法压力

所以对波形绘制任务继续分层，主要分为波形准备（算法部分），和DMA发送部分：
波形准备任务，dma发送完成中断，dma发送任务应该都是相关联的，波形准备好了，dma发送完成，两个任务只有同时发通知，dma发送任务才会唤醒，dma发送任务运行完，通知波形准备任务往另一个缓冲里写数据，使用：

```
空闲缓冲队列 + 就绪缓冲队列 + DMA完成二值信号量
```

波形准备任务
    │ 从free_queue取得空闲缓冲
    │ 绘制波形条带
    │ 把描述符发送到ready_queue
    ▼
DMA发送任务
    │ 从ready_queue取得已完成条带
    │ 启动DMA2D
    │ 等待dma_done_sem
    ▼
DMA2D完成中断
    │ 释放dma_done_sem
    ▼
DMA发送任务
    │ 把已经搬完的缓冲放回free_queue
    │ 最后一块完成后提交LTDC换帧

### 10.6 使用DMA时，屏幕出现重影，条形花屏

DMA和LTDC同时访问SDRAM，会造成总线竞争，如果DMA占用FMC的时间太长了，就会出现条状的重影
更何况在我的项目中，因为我的波形显示不好调用lvgl的API，我是自己准备完数据写入SDRAM的，为了每一帧波形都能完整的显示，我在SDRAM里做了乒乓缓冲，让显示和绘制同步，而控件显示可以调用lvgl的API，所以必须严格按照lvgl的代码规范，在控件的回调函数内调用API，lvgl的timer_handler函数进行绘制。
因为波形用了两块SDRAM，让控件绘制伴随波形绘制去不断切换地址，感觉逻辑过于复杂，刚好LTDC支持双层绘制再合并，波形一层，控件一层
不过这也导致ltdc每次扫描，会将每层的SDRAM都搬运覆盖，波形显示区大小512 * 444 * 2B = 444KB，控件显示区大小1280 * 480 * 2B = 1200KB，一共是1644Kb，LTDC的扫描帧率是60FPS，所以**<u>LTDC的带宽</u>**会达到1644KB * 60/s =**<u> 96MB/s</u>**
DMA的缓冲区大小如果按照整块显示SDRAM，444 * 500 * 2B = 444KB，绘制的帧率受限于算法，姑且暂定为30FPS，**<u>DMA占用的带宽</u>**也会有 444KB * 30 = **<u>12MB/s</u>** 
可能就会有总线竞争或者其它问题，需要依靠仲裁等方法解决
目前我想到了两种治标的方法：

1.允许LTDC去抢占FMC，屏幕刷新永远在第一位，但是不清楚有没有这种硬件上的总线优先级处理方法，或者说总线仲裁
2.调整DMA缓冲区的大小，减少搬运一次的带宽，在搬运完一次CPU处理的那段时间，LTDC肯定会把总线抢过去


为什么使用memcpy的时候不会出现这种情况，memcpy不是一次性把数据都搬过去的，他是一次次搬的，每次会进行读数据，地址递增等操作，使得fmc搬运完数据会等待memcpy，这时候就可以让LTDC完成数据搬运，一般情况下不会有太大问题





### 10.7 总线竞争

LTDC本身使用FMC需要时间，LTDC的频率跟屏幕频率绑定，只能支持60FPS，相当于LTDC使用FMC加从FIFO搬数据加空闲时间一共是13.3ms，如果FMC使用时间过长，DMA在帧中断触发时才会搬运，那点空闲时间根本不够搬运完，就会导致LTDC想用FMC的时候还被DMA占着，如果是小块的DMA只会占一会会，LTDC的FIFO短时间不会出问题，如果大块DMA一直占着，那必定会有现象反馈
