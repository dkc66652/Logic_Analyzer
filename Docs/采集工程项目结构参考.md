# 项目结构

本文规定当前工程的模块职责与依赖边界，不把历史方案当作已实现功能。使用入口见
[文档导航](_说明.md)，启动与内存机制见[系统启动与内存](系统启动与内存.md)，
采集、查询和解析细节分别在对应专题中说明。

## 目录结构

```text
Project/
├─ Code/                       # 项目自行实现的代码
│  ├─ main.c                  # 唯一程序入口与模块装配点，不属于任何业务层
│  ├─ 0_Config/               # 全局编译、组件及链接配置
│  ├─ 1_App/                  # 应用层
│  ├─ 2_Services/             # 服务层
│  ├─ 3_Devices/              # 外部器件驱动层
│  ├─ 4_BSP/                  # 板级支持层
│  └─ 5_Platform/             # 系统基础与平台适配层
├─ ThirdParty/                # 第三方库上游源码与来源、版本及必要改动记录
├─ Docs/                      # 工程文档
├─ Tests/                     # 主机回归测试与测试专用替身，不参与固件构建
├─ Core/                      # STM32CubeMX 生成代码
├─ Drivers/                   # STM32 HAL、LL 与 CMSIS
├─ Middlewares/               # STM32CubeMX 生成的中间件代码（可能不存在）
├─ MDK-ARM/                   # Keil 工程文件
└─ *.ioc                      # STM32CubeMX 配置文件
```

本工程已关闭 STM32CubeMX 的 `main()` 生成。程序入口位于 `Code/main.c`，不属于
任何业务层；工程中必须保持只有一个 `main()` 定义。

`Core/Src/main.c` 可以继续保存 CubeMX 生成且仍被平台层使用的系统配置函数，但不得
再定义程序入口。源码路径变化时，必须同步更新 Keil 工程的文件引用。

## 核心原则

按职责和使用范围组织代码，不机械地按技术类型分类。总体依赖方向如下：

```text
main ──→ App ──→ Services ──→ Devices / BSP ──→ Platform
 │        流程       业务能力       器件/板级操作       芯片平台
 └────────────── 直接装配各模块公开接口 ─────────────→
```

图中表示主要职责和默认依赖方向，不要求每次调用都经过全部层级；具体依赖以本文的
依赖规则为准。这里的依赖指源码依赖，例如包含其他模块头文件，或直接引用其具体实现。

本文区分三类约束：

- 必须遵守的边界：保持唯一入口，不形成循环源码依赖，不跨模块访问私有实现。
- 默认做法：优先按各层职责组织代码，复杂业务能力通过 Services 使用。
- 允许的例外：符合调用方职责的简单公开接口、框架扩展入口和注册回调。例外仍须保持职责清晰，不借此把业务实现放到下层。

下层不得直接绑定上层业务实现、包含上层业务头文件或解释上层私有状态。下层可以保存
注册回调及不透明的 `context` 指针，通过回调、事件或消息向上传递结果；这种运行时调用
不构成反向源码依赖。

## 各层职责与边界

### `Code/main.c`：组合入口

- 负责系统装配、初始化顺序、启动调度器以及启动阶段的日志和异常处理。
- 可以使用启动编排所需的各层公开接口及 FreeRTOS 启动接口，不受普通业务模块的默认层次限制。
- 不实现产品业务、设备驱动、算法或数据处理。
- `main.c` 是唯一系统装配点，直接按前置依赖调用各模块的公开初始化接口；不要求每层都有初始化入口，也不要求按完整层级依次启动。
- 初始化实现由所属模块封装。`main.c` 不直接调用 HAL/LL 硬件操作或 `MX_*` 生成初始化函数，不直接操作寄存器或具体外设句柄。
- 需要任务运行环境的初始化可以在调度器启动后的任务中完成；该时机仍应由接口前置条件和系统装配决定。

当前启动顺序如下，保持原有执行顺序，但将模块装配明确放在入口：

```text
Sys_Init → Tick_Init → Platform_Trace_Init
→ BSP_Board_Init → BSP_FMC_SDRAM_Init → BSP_Led_Init → BSP_LA_IC_Init
→ W9825G6KH_Init → Platform_Runtime_Init
→ LA_Service_Init → Protocol_Service_Init
→ FileSystem_Init → Compression_Service_Init → App_FileSystem_Demo_Init
→ App_Status_Init → App_Protocol_Demo_Init → App_Cpu_Usage_Demo_Init
→ vTaskStartScheduler
```

其中的职责和前置依赖如下：

- `Sys_Init` 位于 `5_Platform/sys/sys_config`，只封装 MPU、Cache、write-through、HAL和系统时钟的基础初始化，并保持该内部顺序；Tick和Trace分别由入口调用自己的公开初始化接口。
- `Tick_Init` 和 `Platform_Trace_Init` 必须在HAL及系统时钟准备完成后调用；平台周期维护依赖Tick已经就绪。
- `BSP_Board_Init` 位于 `4_BSP/board/board`，只准备GPIO、DMA、MDMA共同板级资源。FMC、LED和LA采集硬件分别由各自模块初始化，使用这些共同资源的板级功能必须在资源准备完成后调用。
- `W9825G6KH_Init` 依赖FMC控制器就绪；完成SDRAM器件命令和刷新设置后，发布平台SDRAM MPU访问窗口。使用SDRAM的服务必须在器件就绪并开放访问后初始化。
- LA服务、协议服务和应用各自拥有公开初始化接口；入口按其资源和服务依赖排序。当前序列不代表所有同层模块之间都存在依赖，独立模块可按实际前置条件穿插装配。
- `Compression_Service_Init`在LA与FileSystem初始化后创建工作区互斥锁，不创建后台任务；保存、校验、加载均由调用任务同步执行。

### `1_App`：应用层

- 描述产品流程、状态、模式和对外响应，是服务的使用者。
- 可以组合多个 Service 完成一个产品功能。
- 复杂业务能力优先通过 Services 使用。状态灯、按键、诊断演示等简单板级操作可以调用 BSP 的公开语义接口；具体 Device 已完整封装所需能力时，也可以直接使用其公开接口，不必添加仅转发调用的 Service。
- 不直接操作硬件寄存器、HAL/LL 外设 API 或 CubeMX 外设句柄，硬件实现细节由 BSP、Devices 或 Platform 封装。
- App 可以在实现文件中直接使用 FreeRTOS 创建和编排承载产品流程的任务，也可以使用任务通知、队列、延时等调度机制。
- 普通业务数据接口优先使用项目数据类型、回调或事件定义，避免无必要地暴露 RTOS 类型。明确提供任务协作能力的接口可以公开 `TaskHandle_t`、`QueueHandle_t` 等类型，并说明使用上下文、句柄生命周期和所有权。
- 可复用的通用 RTOS 封装和移植端适配适合放入 Platform；任务优先级、应用启动顺序等产品策略仍由 App 或系统装配决定。不必为了形式分层而包装每一个 FreeRTOS API。
- 只服务于单一应用流程、演示或特定界面的算法和数据转换可以留在 App 的内部子模块。具备明确的独立使用场景或实际跨模块复用需求时，再考虑提取到 Services。

### `2_Services`：服务层

- 提供可复用的业务能力，包括算法、资源整合、状态机、数据存储和中间件适配。
- 可以依赖其他 Service、Devices、BSP 和 Platform，但同层 Service 之间不得形成循环依赖。
- Service 名称应表达实际能力和使用范围，例如专门处理 LA 边沿数据的模块可以命名为 `la_protocol`；不因当前只有一个使用者就强制改名或拆层。
- 不应把具体总线、DMA 控制器或存储介质细节泄漏到公共接口；这些细节应由 Device、BSP 或专用适配模块封装。
- Service 可以用独立任务、队列、信号量或软件定时器实现异步能力。普通业务接口避免无必要地暴露 RTOS 类型；明确提供任务协作或 RTOS 适配的接口可以使用这些类型，并说明上下文、生命周期和所有权。
- 可以按服务职责直接使用第三方算法或中间件的公开 API；适配代码留在服务模块内，不修改第三方原始源码来承载项目业务。

### `3_Devices`：外部器件驱动层

- 封装具体外部芯片的寄存器、命令、时序、状态和初始化流程。
- 通过 BSP 提供的总线或控制器接口访问芯片，可以使用 Platform 提供的延时、临界区等基础能力。
- 不负责描述 MCU 引脚和板级连接，也不直接依赖 App 或 Services。
- 例如 SDRAM 芯片的上电命令和刷新参数属于 Device，FMC 控制器及其板级连接属于 BSP。

### `4_BSP`：板级支持层

- 描述主控与板上硬件的实际连接方式，包括引脚、外设实例、DMA 通道、中断映射和板载器件控制。
- 封装 CubeMX 生成的外设初始化函数、HAL/LL 调用和外设句柄，向上提供板级语义接口。
- 可以依赖 Platform、`Core` 和 `Drivers`，不得依赖 Devices、Services 或 App。
- BSP 只负责“如何连接和操作”，不实现外部芯片自身的完整命令流程或产品业务状态机。

### `5_Platform`：平台层

- 封装与 MCU、RTOS、编译器和链接布局强相关的通用能力。
- 包括系统时钟、MPU/Cache、Tick、延时、异常、日志、内存段属性和 RTOS 适配等。
- 可以依赖 `Core`、`Drivers` 和 `ThirdParty`，不得依赖 BSP、Devices、Services 或 App。
- Platform 的通用能力接口优先隐藏引脚、外设实例等板级细节；实现可以使用本工程选定的时钟、内存布局和输出后端配置，不要求脱离当前硬件后仍能直接运行。
- 纯粹描述 PCB 连接关系的功能归 BSP。日志格式化、锁和输出策略可以归 Platform，UART 实例与引脚绑定属于后端配置；当前后端基于 Core 的生成配置实现可以接受。
- 如果把某个后端放入 BSP，应由组合入口通过回调或操作接口将其接入 Platform，Platform 不直接包含 BSP 具体实现的头文件。

## 辅助目录边界

- `0_Config`：保存影响多个模块或整个构建的配置，例如 FreeRTOS 配置、链接脚本和平台级开关。只影响单个模块的私有常量应留在该模块中。
- `ThirdParty`：保存第三方上游源码，默认不修改或自行新增项目代码，并保留许可证、版本和来源说明。项目适配代码按职责放入所属模块，不混入第三方源码；必要例外遵守下面的维护规则。该目录表示源码来源，不限定调用方只能属于底层。
- `Docs`：保存架构、接口、硬件连接、设计决策和调试记录。
- `Tests`：保存回归用例、测试运行脚本和硬件/RTOS替身；可以通过测试适配器访问模块内部实现，但不得将这些测试专用依赖纳入固件构建，也不得把主机替身验证当作板上时序验证。
- `Core/Drivers/Middlewares`：保存 CubeMX 或 STM32 官方生成、提供的代码。业务代码不得放入这些目录；对生成代码的修改应限制在 `USER CODE` 区或形成明确记录。

### `ThirdParty`：源码维护规则

- 默认保持上游源码及其组织方式，非必要不修改现有代码、不自行新增代码，也不为统一项目风格而重命名、重排或格式化第三方实现。正常引入新库、更新上游版本或补入必要的上游文件，不属于自行新增项目代码。
- 项目配置与适配优先放在 `Code/`：全局组件配置放入 `0_Config`，MCU/RTOS 适配放入 `5_Platform`，业务中间件适配放入相应 Service，硬件操作按 BSP/Devices 的职责组织。能够通过配置、公开接口、回调或外部适配满足需求时，不修改第三方核心源码。
- 仅允许以下必要例外，且均须遵守库的许可证与本工程依赖边界：
  1. 官方文档明确支持的常规操作，例如应用官方补丁、调整指定配置文件、按官方约定实现移植接口或扩展点。能够独立放在 `Code/` 的配置与适配仍放在 `Code/`；只有官方约定确需放在库目录内时，才在 `ThirdParty` 内修改或新增对应文件。
  2. 当前小型移植库最符合实际需求，但无法通过现有配置、公开接口或外部适配满足必要要求时，允许说明原因后进行最小范围的修改或新增实现。不得仅因修改方便或代码量小就使用该例外，也不得把产品业务逻辑混入第三方源码。
- 许可证允许修改，只说明具有修改权限，不等于该修改属于官方支持的常规操作，也不能单独作为修改理由。所有例外均须保留版权、许可证及免责声明，在对应库的说明中记录上游来源和版本、修改原因、涉及文件、官方补丁出处或自定义差异、验证结果，以及后续升级时如何重新应用或移除改动。

当前 FatFs 的 `ff.c` 应用官方 patch-1 与 patch-2，属于官方补丁例外；项目配置与
SDMMC/FreeRTOS 适配仍放在 `Code/`，具体记录见
[FatFs 来源与补丁说明](../ThirdParty/FatFs/README.md)。

## 依赖规则

各层均可按本层职责使用第三方库的公开 API。下表列出项目代码之间的依赖；框架规定的
中断、回调和 hook 桥接按后面的专门规则处理。

| 使用方 | 默认直接依赖 | 允许的补充依赖 | 边界 |
| --- | --- | --- | --- |
| `main.c` | 启动编排所需的各模块公开接口 | FreeRTOS 启动接口 | 不访问模块私有实现，不直接调用HAL/LL硬件操作或MX初始化，不直接操作寄存器或具体外设句柄 |
| App | Services、Platform | 简单板级操作使用 BSP；已封装完整能力的 Device；FreeRTOS 公共 API | 不直接操作 HAL/LL 外设 API、寄存器或 Core 外设句柄 |
| Services | Services、Devices、BSP、Platform | FreeRTOS 公共 API、业务算法和中间件 | 不直接绑定 App 实现，不形成同层循环源码依赖 |
| Devices | BSP、Platform | 按器件职责使用的第三方驱动接口 | 不直接绑定 App/Services，不访问 Core 外设实现 |
| BSP | Platform、Core、Drivers | 板级操作所需的第三方接口 | 不直接绑定 App、Services 或 Devices 的具体实现 |
| Platform | Core、Drivers、平台配置 | 平台相关第三方接口、装配注入的后端 | 不直接绑定 App、Services、Devices 或 BSP 的具体实现 |

补充约束：

- 对 Core 外设句柄以及 Drivers 中 HAL/LL 硬件操作接口的直接依赖收敛在 Platform 或 BSP，避免向上扩散。
- 第三方库按使用职责归属：MCU/RTOS 移植适配放入 Platform，业务中间件适配可以放入 Services，专用库也可以由相应模块直接使用。不为目录层次增加只有转发调用的包装。
- App 和 Services 可以直接使用 FreeRTOS 公共 API 实现任务调度与同步；移植层内部实现由 Platform 或 RTOS 配置负责。业务接口默认隐藏 RTOS 类型，明确承担任务协作或 RTOS 适配的接口允许公开这些类型。
- 允许跨过中间层调用，例如 Service 直接使用 BSP；前提是该依赖符合职责且没有把硬件细节暴露到上层公共接口。
- 禁止直接绑定上层业务实现和形成循环源码依赖；注册回调、事件上报和不透明上下文指针不视为反向源码依赖。
- Core 中的中断入口、HAL 回调和 FreeRTOS hook 可以作为框架要求的桥接点调用所属模块的处理接口。这些入口只承担分发或必要的底层处理，不承载产品流程。
- 板载外设和采集 DMA 事件通常交给 BSP；RTOS Tick、HAL 时间基准和系统异常交给 RTOS 或 Platform，不要求全部经过 BSP。
- 中断回调只执行适合中断上下文的短操作，使用适用的 ISR API，避免阻塞和耗时业务处理。复杂工作转交给拥有该职责的 App、Service 或 Platform 任务。

## 接口与文件组织

- 模块按实际接口组织公开头文件，不强制一个模块只有一个头文件。多文件实现共享的内部声明可放入 `*_internal.h`；其他模块不得包含私有头文件或依赖私有符号。
- 公共符号使用所属模块前缀，避免不同层出现含义不明的全局名称。
- 工程当前将各层根目录同时加入头文件搜索路径，因此不得在不同层创建相同的相对头文件路径。新增模块应优先使用明确、唯一的目录和文件名。
- 按模块提供有明确职责的公开初始化接口，不创建仅为聚合整层模块而存在的初始化入口或 `init` 目录。跨模块装配和启动顺序由 `main.c` 负责；模块内部仍可封装自身基础步骤，例如 `Sys_Init` 的MCU系统准备和 `BSP_Board_Init` 的共同板级资源准备。
- 模块自身初始化可以调用满足前置条件的下层公开操作，例如 Device 就绪后发布平台内存窗口，不因此归属其他层；这种模块职责内的操作不能成为整层启动编排的入口。
- 文件过大本身不是分层错误；多个职责具有独立变化原因时，可以先在模块内部拆分。拆文件、拆职责和跨层迁移分别判断，不因存在算法或代码量大就要求迁入 Services。

## 归属判断

- 某段逻辑只服务于一个模块，就放在该模块内部。
- 被多个业务模块复用，通常提取到 Services。
- 描述具体外部芯片行为，放到 Devices。
- 描述 PCB 连接和 MCU 外设实例，放到 BSP。
- 被多个底层模块复用且与芯片、RTOS 或编译器强相关，放到 Platform。
- 仅负责组装和启动多个模块，放到 `Code/main.c`。
- 不要因为 UART 是外设、算法是软件，就预设它们必须属于某一层；应根据它表达的是产品能力、芯片协议、板级连接还是 MCU 平台能力来判断。
